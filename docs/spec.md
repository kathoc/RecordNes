# RecordNes 仕様書

プレイ記録と再生に特化した NES エミュレーター。目的はスーパープレイ動画の作成。

- 対応: Windows / macOS / Linux / Android（当面は Linux デスクトップのみ実装）
- 配布: GitHub リリース
- 状態: 開発中（v0.x）

## 1. 何を作るか

普通の NES エミュレーターとして遊べることを土台に、次の一点へ全機能を寄せる。

**「プレイした結果を、あとから完全に再現し、動画にできる」**

巻き戻しもスローモーションもコマ送りも、その場を乗り切るための手段であって、
最終的に残る記録は「一度も詰まらずに通した一本のプレイ」に見える。
記録はフレーム単位の入力列なので、どれだけ遅く操作していても、再生は常に実時間 60fps になる。

## 2. コアの選定

### 採用: `@nesjs/core` 2.7.0（MIT / TypeScript）

同一リポジトリ群の `~/Playground/nesterm` で実績があり、必要な足回りが揃っている。

| 要件 | 対応状況 |
|---|---|
| バイナリ・セーブステート | `createBinarySaveState()` / `loadBinarySaveState()` |
| フレーム単位の実行 | `runFrame()` |
| 入力の 1 バイト注入 | `setInput(player, byte)` — 記録の再生にそのまま使える |
| フレーム前フック | `onBeforeFrame` — 再生時の入力差し込み点 |
| 音声 | `setAudioInterface` でサンプル単位のコールバック |
| SRAM | `saveSRAM()` / `loadSRAM()` |

### 実測（2026-09-29、Node 22 / この開発機）

| 項目 | Super Mario Bros.（NROM） | Super Mario Bros. 3（MMC3） |
|---|---|---|
| 同一入力 2 回実行のフレームバッファ一致 | PASS | PASS |
| 同上・音声サンプル累積の一致 | PASS | PASS |
| 中間状態を保存 → 別インスタンスで復元 → 続行した結果の一致 | PASS | PASS |
| 1 フレームの実行時間 | — | 3.21 ms |
| セーブステート作成 | 7,402 B | 0.25 ms / 8,365 B |
| セーブステート復元 | — | 0.31 ms |

検証スクリプトは `tools/spike-determinism.mjs` と `tools/spike-perf.mjs`。

**この数値が設計を決めた。** 1 フレーム 3.2ms に対しセーブステートが 0.25ms なので、
毎フレーム状態を取っても予算の 2% 弱しか使わない。巻き戻しを「最寄りの状態から再計算」
ではなく「その場で復元」で実装できる。

### 見送った案

- **自作コア（TypeScript で 6502 + PPU + APU を書く）** — 効果: 完全な制御。難度: 極大。
  マッパー対応とタイミング精度の作り込みに数週間かかり、既存コアで要件が満たせる以上は割に合わない。
- **既存 C コアの WebAssembly 移植（FCEUX / Nestopia）** — 効果: 精度は最良。
  難度: 大。emscripten ツールチェーンがこの環境に無く、セーブステートの JS 側からの扱いも煩雑。
- **jsnes** — 効果: 枯れている。難度: 小。しかしセーブステートが JSON で重く、マッパー対応も狭い。

## 3. 技術スタック

| 層 | 選定 | 理由 |
|---|---|---|
| 言語 | TypeScript | 同開発者の brickboy と揃う |
| ビルド | Vite | 同上 |
| デスクトップ | Electron + electron-builder | Win/Mac/Linux を 1 コードベースで配布できる |
| 描画 | Canvas 2D（`ImageData` + `image-rendering: pixelated`） | 256×240 では WebGL の利点が薄い |
| 音声 | Web Audio AudioWorklet + リングバッファ | メインスレッドの詰まりに強い |
| 動画書き出し | ffmpeg（`ffmpeg-static` を同梱、無ければ system ffmpeg） | mp4 / H.264 + AAC |
| Android | 将来 Capacitor で同じ `src/` を包む | プラットフォーム依存は `platform/` の 1 インターフェースに閉じる |

`src/` はブラウザで動く純粋な web アプリとして書き、ファイル保存・ffmpeg 起動といった
ネイティブ機能は `PlatformBridge` インターフェース越しにのみ触る。Electron 版と web 版が
それぞれ実装を持つ。Android 対応のときに書き換える場所をここだけに限定するための境界。

## 4. 記録モデル

### 4.1 タイムライン

記録の実体は「フレーム番号を添字とする入力の配列」。

```
frame:  0    1    2    3    4    5   ...
p1:    00   00   08   08   80   81  ...   (1 バイト: A,B,SELECT,START,UP,DOWN,LEFT,RIGHT)
p2:    00   00   00   00   00   00  ...
```

これに加えて次を持つ。

- **キーフレーム** — 一定間隔のセーブステート。巻き戻しとシーク、後日の再開に使う。
- **イベント** — リセット、章の区切り（マーカー）など、フレーム番号に紐づく出来事。

1 フレーム 2 バイトなので、60fps で毎秒 120 バイト。1 時間のプレイでも 432KB にしかならない。
**入力列は常に全部持つ。** 容量を食うのはキーフレームだけ。

### 4.2 記録は ROM 読み込み直後から常に走る

ROM をロードした瞬間に記録が始まり、止める操作は無い。ユーザーが「記録開始」を押し忘れて
名プレイを失う事故を、そもそも起こらなくする。

ただし**保存は明示的**。閉じるときに「保存しますか」とは聞くが、勝手にディスクへは書かない。

### 4.3 記録が消える条件

| 操作 | 既定 | 設定で変更 |
|---|---|---|
| 別の ROM を読み込む | 消える（確認ダイアログあり） | — |
| リセット | 消える | 「リセットで記録を消さない」を ON にすると、リセット自体がイベントとして記録され、タイムラインは続く |

リセットを記録できるということは、リセット技や、リセットを挟む周回プレイもそのまま再現できる。

### 4.4 巻き戻しと合流（splice）

巻き戻しは「タイムラインを縮める」操作として定義する。

```
記録中:  [0 ................ 1000]   ← 現在フレーム 1000
巻き戻し: [0 ........ 850]           ← 850 まで戻す。851..1000 は捨てる
再開:    [0 ........ 850 → 851' ...] ← 新しい 851 以降を書き足す
```

捨てた区間はファイルに残らないので、**保存された記録には巻き戻した痕跡が一切無い**。
再生すると、最初から一度も失敗しなかった一本のプレイに見える。これが本アプリの核心。

巻き戻しの実装は 2 段構え。

- **密リング**: 直近 15 秒分を毎フレーム保存（8.4KB × 900 ≒ 7.5MB）。なめらかに戻せる。
- **疎キーフレーム**: セッション全体を通して 5 秒ごと（1 分あたり 100KB）。
  密リングより古い地点へは、疎キーフレームから入力列を高速再実行して到達する。

### 4.5 スローモーション・コマ送り

実時間の進み方を変えるだけで、記録されるものは変わらない。10% 速度で 100 フレーム操作すれば、
記録には 100 フレーム分が入り、再生は 1.67 秒で終わる。

- スロー: 1/2, 1/4, 1/8, 1/16
- コマ送り: 1 フレームずつ進める。押しっぱなしで連続送り
- 早送り: 2x, 4x, 8x, 無制限（音声は切る）

### 4.6 保存形式 `.rnes`

```
オフセット 0: マジック "RNES" (4B)
           4: フォーマット版 u16
           6: ヘッダ長 u32
          10: ヘッダ JSON (UTF-8)
          ..: バイナリ区画（ヘッダが offset/length で指す）
```

ヘッダ JSON:

```jsonc
{
  "version": 1,
  "createdAt": "2026-09-29T12:00:00.000Z",
  "title": "SMB ノーコンティニュークリア",
  "rom": { "name": "...", "size": 40976, "sha1": "...", "crc32": "...", "mapper": 0 },
  "frameCount": 123456,
  "players": 1,
  "origin": "power",          // または "savestate"（区画 ORIGIN から開始）
  "totalRewinds": 12,         // 参考情報。再現には使わない
  "sections": {
    "INPUT":  { "offset": 0, "length": 246912 },       // frameCount * 2、非圧縮
    "EVENTS": { "offset": ..., "length": ... },        // JSON
    "KEYS":   { "offset": ..., "length": ... },        // キーフレーム索引 + deflate 圧縮した状態
    "ORIGIN": { "offset": ..., "length": ... },        // 任意
    "SRAM":   { "offset": ..., "length": ... }         // 任意
  }
}
```

ROM は同梱しない（著作権）。読み込み時に sha1 で照合し、違えば警告して続行の可否を聞く。

### 4.7 再生と引き継ぎ

- **再生**: 入力列を `setInput` で流し込んで実行。実時間 60fps 固定。
- **引き継ぎ (takeover)**: 再生中に任意のフレームでコントローラーに触れると、そこでタイムラインを
  切り、以降を自分のプレイで上書きする。巻き戻しと同じ splice。
- **後日の続き**: `.rnes` を「続きから」で開くと、最終キーフレームを復元して記録を継続する。

## 5. 入力

### 5.1 キーボード既定

| キー | 機能 |
|---|---|
| 方向キー | 十字キー |
| Z / X | B / A |
| A / S | B 連射 / A 連射 |
| Enter / 右Shift | START / SELECT |
| Backspace（長押し） | 巻き戻し |
| F | コマ送り |
| Space | 一時停止 |
| Tab（長押し） | 早送り |
| 1〜4 | スロー速度 |
| F1 / F2 | ステートセーブ / ロード |
| F5 | 記録を保存 |
| Ctrl+R | リセット |

### 5.2 コントローラー: L をコンビネーションキーに

コントローラーだけで全機能へ届くようにする。**L を押しながら**他のボタンを押すと機能が出る。
L 単独は何もしない（離しても何も起きない）ので、誤爆しない。

| L + | 機能 |
|---|---|
| ← / → | 巻き戻し / 早送り（押している間） |
| ↑ / ↓ | 速度を上げる / 下げる（スロー〜早送りを 1 本の段階で扱う） |
| A | コマ送り |
| B | 一時停止 / 再開 |
| X | ステートセーブ |
| Y | ステートロード |
| START | リセット |
| SELECT | 記録を保存 |
| R | マーカーを打つ（あとで頭出しできる） |

L を使わない通常時:

| ボタン | 機能 |
|---|---|
| 十字キー / 左スティック | 十字キー |
| B / A | B / A |
| Y / X | **B 連射 / A 連射** |
| SELECT / START | SELECT / START |

### 5.3 連射（2 モード）

連射スイッチは 3 状態を巡回する: `OFF → ホールド → トグル`

- **ホールド連射**: 押している間だけ連射。押した瞬間は単発で入り、0.5 秒後から連射に移る
  （brickboy と同じ挙動。連打と押しっぱなしを区別したい場面で効く）。
- **トグル連射**: 一度押すと離しても連射が続く。もう一度押すと止まる。
  シューティングの道中など、ずっと撃ちっぱなしにしたい場面向け。

連射速度は 5〜30Hz で設定可能（既定 15Hz）。**連射で生成された入力もフレーム単位で記録される**ので、
再生は完全に一致する。

### 5.4 4-way / 8-way トグル

ゲームによっては斜め入力が雑音にしかならない。brickboy と同じ考え方で、
十字キーを 4 方向に丸めるモードを持つ。ROM ごとに設定を覚える。

- **8-way**（既定）: 斜めをそのまま通す
- **4-way**: 斜めが出たら、より強く倒れている軸だけを残す。アナログスティックでは象限で判定する

## 6. 動画書き出し

記録が決定的なので、**書き出しは実時間で録画するのではなく、最初から決定論的に再実行する**。
その結果、画面の乱れもフレーム落ちも原理的に入らない。

```
記録 (.rnes) ──▶ ヘッドレス再実行 ──▶ RGBA フレーム ──┐
                        └──▶ PCM サンプル ──┐        ├──▶ ffmpeg ──▶ mp4 (H.264 + AAC)
                                            └────────┘
```

- 解像度: 256×240 の整数倍（1x / 2x / 3x / 4x）。既定 2x（512×480）
- フレームレート: 60000/1001（NTSC 実機準拠）または 60
- 音声: 48kHz ステレオ、AAC 192kbps
- 区間指定: フレーム A〜B だけを書き出せる
- オーバーレイ（任意）: 入力表示、フレーム番号、タイトル

ffmpeg のプロセス起動は Electron の main 側。`ffmpeg-static` を同梱し、無ければ PATH の ffmpeg を使う。

## 7. 画面構成

初心者が迷わないことを最優先にする。上級機能は隠さないが、前に出しすぎない。

```
┌──────────────────────────────────────────────┐
│ [ROM を開く] [記録を保存] [記録を開く]  ⚙設定 │
├──────────────────────────────────────────────┤
│                                              │
│              ゲーム画面 (256×240)             │
│                                              │
├──────────────────────────────────────────────┤
│  ●REC 記録中  12:34.56  (44,532 フレーム)     │
│  ├───────────────────────▓▓▓───────────┤    │ ← タイムライン
│  ⏪ ⏸ ⏩ ｜ 速度 [1x] ｜ 連射 [ホールド] [8-WAY]│
└──────────────────────────────────────────────┘
```

- 記録状態は常に画面に出す。「記録されているかどうか」で迷わせない
- タイムラインはドラッグでシークできる。マーカーは目盛りとして出る
- 設定は後ろに畳む。キー割り当て、連射速度、リセット挙動、書き出し設定

## 8. 完成の条件

1. Super Mario Bros.（NROM）と Super Mario Bros. 3（MMC3）が実速度で遊べる
2. 音が出る
3. キーボードとゲームパッドの両方で操作できる
4. 記録 → 保存 → 読み込み → 再生 が、フレーム単位で一致する（自動テストで検証）
5. 巻き戻して続けた記録を再生すると、巻き戻しが見えない
6. リセットを含む記録が再現できる（設定 ON 時）
7. mp4 が書き出せ、映像と音が同期している
8. 途中で保存し、別プロセスで開いて続きから記録できる

## 9. 検証方針

| 対象 | 方法 1 | 方法 2 |
|---|---|---|
| コアの決定性 | Node 上の総当たりハッシュ比較 | 実機画面のスクリーンショット目視 |
| 記録の再現性 | 記録 → 再生のフレームバッファ hash 一致（自動） | 実際にプレイして目で確認 |
| 保存形式 | 往復テスト（書く → 読む → 同値） | 壊れたファイルを食わせて落ちないこと |
| 動画書き出し | ffprobe で長さ・fps・解像度・音声ストリームを検査 | 書き出した mp4 の先頭フレームを画像で目視 |
| 入力 | 単体テスト（連射の周期、4-way 丸め） | 実機で操作 |

画面に関わる変更の報告には必ずスクリーンショットを添える。

## 10. 遅延（目標 0 フレーム）

「ボタンを押してから画面が変わるまで」を実機以下にする。積み上がる遅延を層ごとに潰す。

### 10.1 どこで遅れるか

| 層 | 素朴に作った場合 | 本アプリ |
|---|---|---|
| 入力の採取 | イベント受信時に変数へ書き、次の rAF で使う → 最大 1 フレーム | **エミュレート直前にポーリング**。0 |
| ゲーム内部の反応遅れ | ソフト側の都合で 1〜4 フレーム | **ラン・アヘッドで打ち消す** |
| 提示 | ブラウザの合成 → 1〜2 フレーム | `desynchronized` キャンバス、vsync 制限解除 |
| 音声 | 100ms 前後のバッファ | 2〜3 フレーム相当（約 40ms）+ 動的レート調整 |

### 10.2 ラン・アヘッド

NES のソフトは、入力を読んでから画面に出すまでに自前で数フレーム使う。
エミュレーターは速く動けるので、**未来を先に計算して見せる**ことでこれを消せる。

毎フレーム、こうする（N = ラン・アヘッド段数）。

```
1. 今の入力で 1 フレーム実行  … 音声はここで採る。映像は捨てる
2. 状態を保存
3. 同じ入力でさらに N フレーム実行 … 最後の 1 枚だけ映像を採る
4. 保存した状態へ戻す
```

エミュレーターの本当の状態は 1 フレームだけ進み、**画面は N フレーム先を映す**。
押した瞬間に結果が見えるので、体感遅延は 0 か負になる。

- コスト: 1 フレームあたり実行が (N+1) 倍。実測 3.2ms/フレームなので N=2 で 9.6ms、
  状態の保存・復元が 0.56ms。16.6ms の予算に収まる
- N は 0〜3 で設定。既定 1。起動時に実測して、予算を超える段数は選べなくする
- **記録には一切影響しない。** 3 の実行は捨てられ、記録されるのは 1 の結果だけ

### 10.3 入力を遅らせない

- キーボードは `keydown` / `keyup` でビットを立てるだけ。**読むのはエミュレート直前**
- ゲームパッドは `navigator.getGamepads()` をエミュレート直前に呼ぶ。
  イベント化されないので、ポーリング位置がそのまま遅延になる
- 連射の位相も、実時間ではなくフレーム番号で決める。早送り・スロー中でも記録と一致する

### 10.4 提示

- `canvas.getContext("2d", { desynchronized: true })` で合成待ちを外す
- Electron は `--disable-gpu-vsync` と `--disable-frame-rate-limit` を付け、
  `backgroundThrottling: false` にする
- 1 回の `requestAnimationFrame` の中で「入力ポーリング → エミュレート → 描画」を閉じる。
  またいだ瞬間に 1 フレーム増える

### 10.5 測る

遅延は体感で語らない。`?perf=1` で次を記録し、画面に出す。

- 入力イベント受信からエミュレート開始までの実時間
- 1 フレームのエミュレート時間（ラン・アヘッド込み）
- rAF 間隔のばらつき
